# 文字解谜游戏 · 需求文档（v0.1 草案，待评审）

日期：2026-09-06
状态：**草案** —— 第 12 节列出了需要拍板的决策点（D1~D6），确认后进入实现方案设计与开发。
定位：一个全新的小游戏，与仓库现有《立方数独 3D》相互独立。

---

## 1. 一句话定义

一款**纯文字/轻视觉的网页解谜游戏**：玩家在若干"场景页面"之间穿行，每个场景用文字描绘环境、
埋有可点击的线索与谜题；**达成条件**（拿到钥匙道具、答对密码、触发剧情标记）才能**跳转到下一个场景**，
层层推进揭开故事真相，最终走向不同结局。

- 类"仙剑味" = **中式古风 + 剧情悬念 + 古典机关谜题**（灯谜、诗谜、八卦方位、铜锁机关），
  而不是战斗/RPG 数值。
- "只有文字解密" = 谜题全部通过**阅读、推理、文字/数字输入**完成；点击、选择只是交互外壳，
  不做找物、拼图等重度点击玩法。

## 2. 玩法原型（用户原始诉求 → 设计转译）

| 你的描述 | 设计转译 |
|---|---|
| "好多页面之间达成不同条件跳转" | 场景 = 页面；跳转由条件系统（道具/线索/谜题答案/剧情标记）把守 |
| "类似仙剑那种解密" | 中式古风世界观，谜题素材取自传统文化（灯谜、对联、干支、八卦、账房锁） |
| "只有文字解密的那种最好" | 全部信息用文字呈现，谜题靠读与想，不靠眼疾手快 |
| "先出需求文档再决定怎么做" | 本文档 + 第 11 节技术方案候选 + 第 12 节决策点 |

## 3. 同类游戏调研（2026-09-06 联网检索）

调研目的：确认"条件跳转式文字解谜"的成熟做法，避免闭门造车。

| 游戏 | 值得抄的设计 |
|---|---|
| 锈湖系列 / Cube Escape | 场景内点选线索 → 道具 → 解锁新场景；谜题与剧情隐喻互扣；多结局 |
| 迷失岛 / 南瓜先生（胖布丁） | 非线性探索、二周目差异、收集成就与结局彩蛋；"解谜关键在于发现规则" |
| 古镜记 | 国风文字推理标杆：限时证词收集、**线索合成**（多条线索推出新证词）、用新证词对质破谎 |
| 疑案追声 Unheard | 开放式叙事：线索自由发掘、同一批线索反复回听/回看，答案靠交叉印证 |
| 文字冒险 / 橙光 / Twine | 场景 = 状态机节点，**flag（剧情标记）驱动条件跳转**是几十年的成熟范式 |

**提炼出的 6 条设计法则**（本项目直接采纳）：

1. **场景即状态机节点**：跳转关系是显式的"条件 → 目标"规则表，不是散落的 if/else
   （业界共识：文本冒险的分支用状态机 + flag 管理，避免条件泥球）。
2. **线索—谜题—门槛三件套**：每个门槛（锁）的钥匙必须是玩家在游戏内读到/拿到的信息，
   公平可推理，杜绝"瞎猜答案"。
3. **信息可回看**：见过的证词、拿到的道具永久保留在"笔记/背包"里，迟到的灵感随时能翻旧账。
4. **交叉印证产生高级谜题**：A 场景的数字是 B 场景的锁码；多条线索可"合成"出推论
   （锈湖与古镜记的共同精髓）。
5. **多结局 = 关键选择 + 收集度**：结局数量少而精，每个结局有明确的达成路径。
6. **卡关有兜底**：分层提示（方向 → 收窄 → 答案），保证玩家不会死卡在某一步。

## 4. 玩家体验目标（做完了应该是什么感觉）

- 打开后**双击 HTML 即玩**，像读一本会回应你的志怪小说。
- 每一扇打不开的门都让人惦记；每一次跳转成功都有"我推理出来了"的爽感。
- 通关后想二周目：因为知道还有别的结局和漏掉的细节。
- 手机上也能舒服地玩（竖屏、大按钮、无悬浮输入框依赖）。

## 5. 核心玩法循环

```
阅读场景文字 → 点击可疑之处（热点词/物件）→ 获得线索/道具（自动记入笔记/背包）
   → 用线索解开谜题（输入密码 / 选择答案 / 组合道具）→ 达成条件
   → 解锁跳转 → 进入新场景 → …… → 终章抉择 → 结局
```

## 6. 功能需求清单（P0 必须 / P1 应该 / P2 可选）

| 编号 | 功能 | 优先级 | 需求要点 |
|---|---|---|---|
| F1 | 场景系统 | P0 | 每个场景 = 独立"页面"（同一 HTML 内切换视图）：标题、环境描写、热点、谜题、出口 |
| F2 | 条件跳转引擎 | P0 | 出口规则 = `{目标场景, 解锁条件}`；条件不满足时点击出口给出**具体反馈**（"门被铜锁扣住"而不是"不能去"）；已解锁出口与未解锁出口视觉可区分 |
| F3 | 线索与背包 | P0 | 点击热点获得线索/道具；背包可查看、可选用；关键线索自动归档进笔记 |
| F4 | 谜题交互 | P0 | 至少支持：密码/文字锁输入框、单选/多选问答、道具组合；答案校验宽松（忽略空格、支持近义写法） |
| F5 | 存档读档 | P0 | localStorage 自动存档（场景、背包、flag、笔记、已解谜题）；刷新恢复；可重开新档 |
| F6 | 笔记（线索档案） | P1 | 见过的证词/文字线索按章节归档、随时回看；线索合成推论（收集到 A+B 自动解锁推论 C）在此展示 |
| F7 | 多结局 | P1 | 按关键选择 + 收集度分支；结局页写明结局编号/名称，鼓励再玩 |
| F8 | 分层提示系统 | P1 | 每个谜题 2~3 级提示（点拨 → 收窄 → 接近答案）；使用提示不惩罚但计数（结局可反映） |
| F9 | 流程总览 | P2 | 章节/场景地图（去过的点亮、未去过的暗），进度与收集度统计 |
| F10 | 氛围包装 | P2 | 打字机式文字浮现、Web Audio 合成音效（翻页/解锁/胜利，沿用数独项目的合成方案，零素材）、古风 CSS 视觉、可开关 |
| F11 | 结局图鉴/成就 | P2 | 达成过的结局与彩蛋留档，支持二周目差异（已读过的话可快进） |

**明确不做（非目标）**：战斗/养成/数值系统；账号与云存档；语音；需要联网或构建工具链才能玩的任何东西；
自由键入命令的 parser 式交互（选项制对移动端更友好）。

## 7. 谜题类型库（内容弹药库，按实现成本标注）

| 类型 | 示例 | 成本 |
|---|---|---|
| 密码/文字锁 | 匾额笔画 → 四位铜环锁 | 低 |
| 灯谜/字谜/藏头诗 | 一首诗藏开门暗语 | 低（成本在写文案） |
| 藏在文字里的谜 | 错别字连读成句、谐音、标点藏头 | 低中（特色，"纯文字"味道最浓） |
| 多场景联动线索 | 大堂账本的数字 = 禁房锁码 | 中（锈湖精髓，必备） |
| 线索合成 | 证词A + 账目B → 推论C（自动或手动合成） | 中 |
| 证词矛盾/对质 | 两人说法冲突，选出破绽 | 中 |
| 逻辑小题 | 谁说谎、排座位、干支纪日推算 | 中 |
| 道具组合/使用 | 灯油 + 火折子 → 点灯照出暗字 | 中 |
| 排序/复原 | 残页按点选排序复原成一封信（点选完成，非拖拽拼图） | 中 |
| 方位/阵法 | 八卦、九宫方位锁 | 中高 |

内容红线（公平性）：**每道谜题的答案，其线索必须已在游戏内出现且可回看**；
答案输入支持宽松匹配；任何谜题不得依赖场景外的知识。

## 8. 剧情框架提案（推荐方案，可整体换皮）

> 详细剧本在开工后另出 `docs/剧情与谜题蓝图.md`（全场景清单 + 跳转条件表 + 谜题-线索映射表），
> 本节只定骨架。

**推荐：《长夜灯》—— 中式志怪·荒山客栈**（最贴合"仙剑味"，古典谜题素材最丰富）

- 一句话：暴雨夜，赶路书生投宿荒山客栈；客栈规矩古怪——"灯不灭，人勿离"。
  天亮之前，他要弄清前一位住客为何没有走出这道山门。
- 结构：序章（教学）+ 三幕 + 终章抉择，约 15~20 个场景。

| 章节 | 场景示例 | 关键谜题/门槛 |
|---|---|---|
| 序章·山道 | 山道 → 破庙 | 教学：点击热点、看笔记、解一盏灯谜开门进山 |
| 第一幕·入宿 | 大堂 → 柜房 → 后院 | 台房铜锁（匾额笔画线索）；后院井边的当票引出禁房 |
| 第二幕·真相 | 禁房 → 地窖 → 祠堂 | 禁房锁码=大堂账本数字（跨场景联动）；藏头诗；证词对质"谁在说谎" |
| 终章·子时 | 祠堂祭坛 | 用此前收集的关键道具/推论做**最终抉择**（揭穿 / 同情 / 独自逃离） |

- 结局 4 个：**天亮启程**（普通）/ **灯长明**（真结局：集齐证据链再抉择）/
  **灯灭**（坏结局：关键选择错误）/ **灯影中人**（隐藏结局：全部彩蛋收集）。

**备选题材**（换皮不换骨，引擎与谜题库完全复用）：
- 《雾锁公馆》：民国洋馆遗产悬疑（账本、电报、留声机）。
- 《寂静航路》：科幻孤船，船员接连失踪（日志、舱室权限码）。

## 9. 数据结构草案（场景 Schema —— 引擎与内容的接口）

内容全部声明式数据（开发时内嵌在 HTML 的 `<script type="application/json">` 中，
见第 11 节方案 A 的理由），写剧情 = 填数据，不改引擎：

```json
{
  "id": "inn_hall",
  "chapter": 1,
  "title": "客栈大堂",
  "ambient": "雨声渐歇。堂内一盏白灯笼明明灭灭，柜后的老者头也不抬。",
  "hotspots": [
    { "id": "ledger", "label": "柜台上的账本",
      "text": "账册夹页里压着半张当票……典当人一栏写着你的名字。",
      "gives": { "note": "当票", "item": "当票" } }
  ],
  "puzzles": [
    { "id": "counter_lock", "type": "code", "prompt": "抽屉上一把四位铜环锁",
      "accept": ["七二四九", "7249"],
      "hints": ["抬头看看堂上的匾额。", "匾额四个字，笔画各是几画？"],
      "onSolve": { "item": "铜钥匙", "flag": "counter_open" } }
  ],
  "exits": [
    { "to": "backyard", "label": "推门去后院", "requires": {} },
    { "to": "forbidden_room", "label": "上楼 · 禁房",
      "requires": { "items": ["铜钥匙"] },
      "failText": "楼梯口的门被铜锁扣住，纹丝不动。" }
  ]
}
```

`requires` 统一表达四类条件：`items`（持有道具）、`flags`（剧情标记）、
`solved`（已解谜题）、`notes`（已获线索）；可任意组合。

## 10. 防死锁与体验保障（设计红线）

1. **无死档**：任何结局从任何存档状态都必须可达 —— 蓝图阶段就做"条件图可达性"人工核对，
   开发后写脚本自动校验（每个出口/谜题的所需条件都有获取途径且路径不经过不可回访的场景）。
2. **线索不灭失**：热点可反复查看；一次性消耗的场景（如门被炸开）其线索提前进笔记。
3. **不迷路**：每个场景至少一条已解锁的退路；未解锁出口的反馈文字要暗示"缺什么类型的线索"。
4. **卡关兜底**：F8 分层提示；同一谜题提示用尽仍未解，第 3 级直接给出答案（解谜游戏比拼的是
   推理过程，不该在 doorway 上惩罚玩家）。

## 11. 技术方案候选（"怎么做"的三个选项）

| 方案 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| **A. 单文件 HTML（推荐）** | 沿用本仓库惯例：一个 `*.html` 内含样式、引擎、剧情数据（JSON 内嵌），零依赖双击即玩 | 与仓库"单文件、零依赖、离线可玩"完全一致；`file://` 直开没有任何限制；好分享好备份 | 文件会随剧情变大（估 100~200KB，数独项目已验证此规模无压力） |
| B. 数据外置 | 引擎 HTML + 单独 `scenes.json` | 写内容最舒服、可程序化校验 | **`file://` 协议下 fetch 本地 JSON 会被浏览器 CORS 拦截**，双击即玩就没了，得起本地服务器 |
| C. 框架/多页面 | Vue/React + 路由，真·多页面跳转 | 工程化、组件化最彻底 | 引入构建链与依赖，与"离线双击可玩"冲突；对本项目体量过重 |

**推荐路线：A 为壳、B 为魂** —— 数据按第 9 节 Schema 以 JSON 形式内嵌在单文件里
（引擎只认数据，不认识具体剧情），将来若要扩成多章节大作，把 JSON 抽出去换成 B/C 都是无痛迁移。

## 12. 决策点清单（需要你拍板）

| 编号 | 问题 | 选项 | 推荐 |
|---|---|---|---|
| D1 | 题材世界观 | A 中式志怪《长夜灯》/ B 民国公馆 / C 现代怪谈 / D 科幻孤船 | **A**（仙剑味最浓，古典谜题素材多） |
| D2 | 谜题口味 | A 纯文字推理为主，点击仅拾取线索 / B 加入较多点击式小机关 | **A**（符合"只有文字解密最好"） |
| D3 | 规模 | A 先做试玩版（序章+第一幕，约 6 场景）验证手感再决定全量 / B 直接做全量（15~20 场景 + 4 结局） | **A**（两步走，试玩版本身也是完整可分享的小品） |
| D4 | 结局数量 | 3 / 4 / 更多 | **4**（普通/真/坏/隐藏，数量克制、路径清晰） |
| D5 | 放哪里 | A 本仓库新文件（如 `changye.html`）+ README"游戏合集"加一行 / B 新建独立仓库 | **A**（延续合集惯例） |
| D6 | 技术方案 | 第 11 节 A / B / C | **A**（数据内嵌 JSON，未来可无痛外置） |

**拍板结果（2026-09-06，已确认）**：

- **D1 → 中式志怪《长夜灯》**，但整体质感以**锈湖（Rusty Lake）为北极星**：诡、静、暗，
  "每个场景是一只谜题盒"，谜题与剧情隐喻互扣，有超越现实的意象（会吃名字的灯、没有脸的守灯人、
  把自己画进画里的画师）。
- **D2 → 锈湖式机关谜题**（原推荐 A 的修正）：谜题的**核是文字线索**（笔画、欠条、口诀、镜铭、卦诗），
  **形是可把玩的机关装置**（转轮锁、算盘、九钉匣、陶坛阵、八卦门）——文字解密为魂、机关为皮；
  仍不做找物海、限时、动作类玩法。
- **D3 → 直接做全量**（用户拍板"一次完成"；试玩版降级为里程碑 M2 内部节点，不再单独停下等确认）。
- **D4 → 4 结局**；**D5 → 本仓库新文件 `changye.html`**（README 合集加行）；**D6 → 方案 A 单文件**。

## 14. 验收标准（Definition of Done）

- [ ] Chrome/Edge 双击 `file://` 直开即玩，全程离线；
- [ ] 新档到每个结局全流程可通；**自动化可达性校验**证明无死档；
- [ ] 每道谜题的答案线索均可在游戏内获得并回看（蓝图映射表逐项核对）；
- [ ] 存档刷新/关闭浏览器后完整恢复；重开新档功能正常；
- [ ] 手机竖屏可完整游玩（触控目标 ≥ 40px，无 hover 依赖）；
- [ ] 未满足条件时的出口反馈明确指向"缺什么"；提示系统三层可用；
- [ ] Playwright 测试（沿用 `tests/` 惯例）覆盖：全结局通关流程、存档恢复、代表性谜题解答、跳转条件正反例。
